# 초기 화면 SSR 전환을 위한 인증 흐름 개선 기록

관련 이슈: [#303](https://github.com/100-hours-a-week/KTB4-11th-FE/issues/303) · 이전 인증 개선: [#158](https://github.com/100-hours-a-week/KTB4-11th-FE/issues/158)

## 작업 목적과 범위

사용자가 첫 화면의 실제 내용을 더 빨리 볼 수 있도록, 브라우저에서 처리하던 인증 판단을 가능한 범위부터 Next.js 서버로 옮겼다.

이번 작업은 **데이터 SSR을 위한 기반 작업이면서 인증 가드 자체의 변경**이다. 유효한 액세스 쿠키가 있으면 서버에서 사용자 조회와 로그인·온보딩 분기를 처리한다. 홈·마이페이지의 계좌 데이터를 서버에서 조회해 완성된 첫 화면을 제공하는 작업은 아직 포함하지 않았다.

SSR은 서버의 데이터 조회 결과를 초기 화면에 포함하는 방식이다. 버튼·모달·실시간 갱신까지 모두 서버로 옮기는 것은 아니다. 이번 작업에서도 카카오 로그인 버튼과 세션 복구는 클라이언트에 유지했다.

## 왜 인증 흐름부터 변경했나

기존에는 다음 순서로 인증을 확인했다.

`페이지 수신 → JS 다운로드·실행 → /users/me 조회 → 인증·온보딩 판단 → 하위 화면 표시`

보호 화면의 클라이언트 가드는 사용자 조회가 성공하기 전까지 하위 화면 대신 스플래시를 반환했다. 현재 구조를 유지한 채 하위 화면의 데이터만 SSR로 전환하면, 브라우저의 인증 확인을 기다리는 조건이 남을 수 있었다.

기존에 완성된 SSR 화면이 있었는데 스플래시가 가린 문제를 고친 것은 아니다. **앞으로 서버에서 초기 데이터를 준비할 때, 인증 판단도 그 서버 흐름에서 사용할 수 있도록 정리한 것**이다. 인증 가드 변경이 모든 서비스의 SSR 도입에 필수인 것은 아니지만, 우리 서비스의 보호 화면을 일관되게 전환하기 위해 먼저 다룬 의존 작업이다.

[#158](https://github.com/100-hours-a-week/KTB4-11th-FE/issues/158)은 인증 판단에 사용하던 무거운 계좌 목록 API를 가벼운 `/users/me`와 `onboarding_completed`로 변경한 작업이다. 이번 작업은 같은 API를 유지하면서 **호출 주체와 시작 시점을 브라우저에서 서버로 옮긴다**는 차이가 있다.

## 개선 전 측정

2026-10-26 실제 배포 환경에서 Slow 4G·캐시 비활성화·CPU 제한 없음 조건으로 경로별 5회 측정했다. 새 문서 탐색 시작부터 Performance 캡처에서 표시가 확인된 시점까지의 근삿값이다.

| 측정 경로                  | 완료 기준                                           | 중앙값 |        범위 |
| -------------------------- | --------------------------------------------------- | -----: | ----------: |
| 비로그인 `/` 직접 접속     | 로그인 버튼이 명확하게 표시됨                       | 6.37초 | 6.31~6.39초 |
| 로그인된 `/home` 직접 접속 | 실제 잔액·보유 종목·최근 매매 표시 및 스켈레톤 해제 | 6.37초 | 6.34~6.79초 |

홈은 선택 계좌가 저장된 상태이며, 카카오 로그인 과정과 종목 로고 전체 로딩은 제외했다. 로그인 버튼은 페이드인 효과가 있어 최초 픽셀 표시 시점과 차이가 있다.

비로그인 `/`에서는 아래 흐름이 5회 모두 확인됐다.

`JS 로딩·실행 → /users/me 401 → CSRF 조회 → 토큰 재발급 401 → 로그인 UI 표시`

사용자 정보 요청은 약 4.2초에 시작했고, 이후 인증·재발급 실패 확인까지 약 1.8초가 추가됐다. 이는 제한된 네트워크의 왕복 시간을 포함한 결과이며 백엔드 처리 시간만을 의미하지 않는다.

## 실제 작업과 해결한 문제

| 문제                                                  | 변경 내용                                                       | 해결 범위                                               |
| ----------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------- |
| 인증 조회가 브라우저 JS 실행 뒤에 시작됨              | `getServerUser`가 페이지 요청의 액세스 쿠키로 `/users/me` 조회  | 유효한 세션의 인증·온보딩 판단을 서버에서 처리          |
| 여러 서버 레이아웃에서 같은 사용자를 조회할 수 있음   | React `cache`로 현재 렌더 요청 안에서 조회 재사용               | 같은 요청의 중복 조회 방지                              |
| 서버 결과를 브라우저가 몰라 다시 조회할 수 있음       | `UserHydration`으로 프로필을 React Query의 `['me']` 캐시에 전달 | 기존 `useUserQuery`에서 결과 재사용                     |
| 사용자별 응답이 다른 요청과 공유될 위험               | 서버 fetch에 `no-store` 적용, 요청별 QueryClient 생성           | 사용자별 데이터 분리, 토큰은 클라이언트에 전달하지 않음 |
| 인증 장애와 실제 비로그인을 구분해야 함               | 401만 세션 복구로 넘기고 서버·네트워크 오류는 오류 처리         | 장애를 이유로 로그인 화면으로 보내는 오판 방지          |
| 온보딩 완료 직후 안내 화면이 필요함                   | 완료 여부 검사를 계좌 생성 페이지로 이동                        | `/onboarding/complete`는 로그인 상태에서 접근 유지      |
| 로그아웃 후 이전 세션의 서버 렌더 결과가 남을 수 있음 | 캐시 정리 후 새 문서로 이동                                     | 이전 사용자 정보·리다이렉트 재사용 방지                 |

서버 조회에는 브라우저 Axios를 사용하지 않았다. 기존 Axios의 토스트·화면 이동·브라우저 쿠키 기반 재발급 로직을 서버에서 그대로 실행할 수 없기 때문에, 서버용 조회 함수를 별도로 분리했다.

## 세션 만료 처리를 클라이언트에 남긴 이유

실제 쿠키 설정에서 `access_token`은 Path가 `/`이지만 `refresh_token`은 `/api/v1/auth`다. Next 서버는 일반 페이지 요청에서 액세스 쿠키를 받을 수 있지만 재발급 쿠키는 받을 수 없다.

따라서 다음처럼 역할을 나눴다.

| 상태                     | 처리                                    |
| ------------------------ | --------------------------------------- |
| 유효한 액세스 쿠키       | 서버에서 사용자 조회와 분기 처리        |
| 액세스 쿠키 만료·누락    | 브라우저에서 기존 CSRF·재발급 흐름 수행 |
| 세션 복구 중             | 스플래시 유지                           |
| 복구 성공                | 목적 화면 표시 또는 이동                |
| 최종 401로 비로그인 확정 | 로그인 화면 표시                        |
| 서버·네트워크 오류       | 오류 화면 표시                          |

세션 복구 중 로그인 화면을 먼저 보여주면 자동 로그인 사용자에게 화면이 잠깐 나타났다 사라질 수 있다. 이를 피하기 위해 최종 구현은 복구 결과가 나올 때까지 스플래시를 유지한다. 별도의 최소 표시 시간은 추가하지 않는다.

**이번 변경만으로 비로그인 사용자의 인증 확인·재발급 대기까지 제거한 것은 아니다.** 이 부분을 줄이려면 서버의 세션 복구 가능 여부를 포함해 쿠키·인증 구조를 별도로 검토해야 한다.

브라우저 MSW가 켜져 있거나 로컬 API 쿠키를 Next 서버가 받지 못하는 환경도 클라이언트 가드를 사용한다. 백엔드의 새 쿠키는 기존 브라우저 응답 경로로 처리하며, 서버 렌더링 중 쿠키를 임의로 생성하거나 재발급하지 않는다.

## 검증한 내용과 남은 검증

| 검증                                   | 결과·범위                                                                                                  |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 실제 배포 세션으로 서버 조회 가능 여부 | 로컬 Next 서버가 실제 액세스 쿠키를 전달한 `/users/me` 요청에서 200 및 정상 필드 확인                      |
| 서버 조회 함수 테스트 5개              | 쿠키 전달·응답 분리·401·서버 오류·타임아웃·잘못된 응답 처리 통과                                           |
| 로컬 프로덕션 HTTP 검증 12개           | 로그인·온보딩 분기, 완료 화면 접근, 복구 경로, 장애 처리, 요청 중복 및 사용자 격리 확인                    |
| 테스트 쿠키 기반 브라우저 검증         | 만료 액세스 → CSRF → 재발급 → 사용자 재조회 → 마이페이지 표시 확인, 정상 세션의 중복 사용자 조회 없음 확인 |
| 타입·린트·프로덕션 빌드                | 구현 단계 통과, 기존 린트 경고 5개                                                                         |
| 최종 스플래시 유지 분기 수정           | 타입·변경 파일 린트·포맷 검사 통과, 수정 후 브라우저 회귀 검증 필요                                        |
| 변경한 전체 코드의 실제 배포 환경 동작 | 미검증                                                                                                     |
| 개선 후 표시 시간 및 단축량            | 미측정                                                                                                     |

기존의 실제 세션 서버 요청 성공은 서버 조회 가능성의 근거다. 변경한 전체 인증 흐름을 운영 환경에서 검증한 결과와는 구분한다. 로컬 테스트 API 결과도 실제 성능 개선량으로 사용하지 않는다.

## 이 작업으로 가능해진 후속 작업

1. **마이페이지 초기 데이터 SSR**: 서버에서 인증된 사용자 정보를 얻고 프로필을 재사용할 수 있다. 선택 계좌 전달 방법을 정하면 계좌 잔액·수익률·거래 횟수의 초기 조회도 추가할 수 있다.
2. **홈 초기 데이터 SSR**: 같은 인증 흐름 위에서 잔액·보유 종목·최근 매매를 서버에서 준비하고, 첫 화면에 포함하는 작업을 진행할 수 있다.
3. **실제 표시 성능 비교**: 인증 가드 변경과 각 화면의 데이터 SSR 효과를 나눠 측정할 수 있다.

선택 계좌는 현재 `localStorage`에 있어 서버가 직접 읽을 수 없다. URL·쿠키 등으로 전달할지, 첫 진입의 기본 계좌 정책을 둘지 후속 설계가 필요하다. 클릭·모달·계좌 변경·실시간 갱신은 계속 클라이언트가 담당할 수 있다.

SSR은 API 자체를 빠르게 만드는 작업이 아니다. **브라우저 JS 실행 뒤에 시작하던 인증·조회 대기를 앞당겨 실제 콘텐츠가 더 빨리 표시되는지 확인하는 작업**이다. 개선 후에는 같은 사용자·선택 계좌·API·캐시·네트워크 조건으로 반복 측정해야 하며, 현재 시점에서는 단축량을 확정하지 않는다.

## 실행 및 설정 참고

- `API_BASE_URL`은 Next 서버용 백엔드 주소이며 선택 사항이다. 없으면 `NEXT_PUBLIC_API_BASE_URL`을 사용한다.
- 실제 서버 경로 검증은 MSW를 끄고 수행한다. 운영 쿠키의 Domain·Path·Secure와 서버의 백엔드 접근도 확인한다.

```sh
node --test src/features/auth/server/__tests__/requestServerUser.test.mjs
npm run typecheck
npm run lint
npm run build
```
